# 创造性检索工作流

## 目标和边界

本工作流用于申请前的创造性检索。案件默认是尚未提交的技术交底书，工作目标不是给已申请案件出审查答复，而是判断技术方案的可保护边界，并把检索结论反馈给后续申请文本。

默认交接：Agent 检索并列候选，用户把全文放入案件目录后再深入比对，不得因等待下载而虚构全文结论。用户明确要求用 HimmPat MCP 下载专利时，按该要求下载专利；论文仍由用户下载。未要求时不自行下载、不用全文接口绕过交接。

章节按理解交底 → 检索 → 交接 → 核验 → 评述 排列，便于查阅，不是每次必须从头执行。由 `SKILL.md` 选定节点后再读对应章节。

- 用户只要检索式或候选清单：以第 3 节的交接物完成任务。已授权后续分析但缺必需全文时，暂停依赖该全文的判断，继续可独立完成的授权部分。用户明确要求用 HimmPat MCP 下载专利时按该要求下载；未要求时不自行下载。
- 对比文件整份转不出可用文字：暂停该文件的全文判断，请用户拷官方文本；未经用户要求不要整本 OCR、逐页截图或用 HimmPat 读细节。交底正文可抽、公式或关键数据在嵌图里：按第 1 节补读，不是卡点。
- 全文已在案件目录：从第 4 节核验起，不要无故重出检索式。
- 已有评述且方案未实质变化：不要重写评述，除非用户要求或对比文件已换。
- 方案已改版：继承未变事实，重新核对对比关系、效果、技术问题和保护接口。

## 方案版本与工作底稿

最终交付文件只表示当前有效方案；工作底稿用于保持事实、证据和决策的连续性。案件可以按需要建立以下中间文件，不要求每次方案变化都复制一整套文件：

```text
workbench/
  00_案件状态.md
  01_交底事实与术语.md
  02_检索要素与检索日志.md
  03_特征-文件-效果-证据.md
  04_保护范围决策.md
  05_说明书支撑与实施例计划.md
  06_文本逻辑审计.md
```

处理原则：

1. 初始技术方案记为 `V1`。只有组分、结构、步骤、关系、参数或主张效果等技术内容发生实质变化时，才建立 `V2` 等新版本；单纯修改措辞、排版或一般性的权利要求缩小，不必强制建立新方案版本。
2. 方案实质变化时，在 `00_案件状态.md` 或 `02_检索要素与检索日志.md` 中简要记录修改原因、保留内容、删除内容、新增内容和需要重新验证的效果；`01_交底事实与术语.md` 仍以交底书事实为主，并把当前方案版本明确为唯一工作对象。
3. `02`至`06`中的当前结论以当前方案版本为准。未改变且已经核实的事实可以继承；受方案变化影响的对比关系、技术效果、实际技术问题和保护范围必须重新核对，不能直接沿用旧结论。
4. 创造性不足不当然意味着必须改方案。先区分：检索不充分则补充检索，效果证据不足则补实验或降低表述，保护范围过宽则调整权利要求，核心方案与现有技术重合时才考虑形成新的技术方案版本。
5. 新版本检索应同时检查新增或调整特征，以及新版本的完整组合。旧版本的最接近文件可以作为检索线索，但必须重新判断其是否仍然适合作为当前版本的最接近现有技术。
6. 当前版本确定后，在本轮授权范围内生成或更新案件目录中的 `创造性检索分析.md` 和专利文本。旧版文件默认保留，在工作底稿中标明采用版本及主要变化；文件整理、重命名与历史保留按 `case-markdown-git.md`，更新当前稿不自动授权删除旧稿。不要求对旧版本重新进行与当前版本同等程度的论证。

## 创造性风险后的可推进方向

创造性检索的交付目标是帮助客户作出下一步保护决策。当前独立权利要求风险较高时，先区分以下状态：

- 已有完整单件公开或结合证据，足以支持当前范围风险较高；
- 全文、日期、效果对照或技术事实不足，暂不能稳定判断；
- 检索范围或最接近文件选择仍不充分，需要补充检索；
- 当前独权风险较高，但交底中仍可能存在可形成不同保护方案的已公开内容。

除非用户明确只要结论、检索式或候选清单，否则对后三类以及第一类中的可调整部分继续检查可推进方向。方向必须来自当前交底、已核实的技术资料或可以明确安排验证的事项，不能靠拼接多件文件或补造技术内容。按案件适用情况检查：

1. 尚未写入独权、但与其他特征有明确技术关系的组成、结构、步骤、位置、顺序或控制条件；
2. 交底中已有依据的用途、制备、处理、检测、产品或其他有独立保护价值的对象；
3. 参数、范围、选择条件或工艺窗口，及其可能需要的对照和重复性验证；
4. 能与最接近方案对齐的特殊效果、相互作用或技术问题，但仅在证据支持或可执行验证的范围内提出；
5. 最接近文件、技术问题或方案版本是否需要重新选择，及其对保护范围的影响。

每个候选方向用条目记录：方向内容；交底或资料依据；相对现有技术的实际区别；需要补的全文、技术确认、检索或实验；可能进入的权利要求类别；主要法律、支持、实施或创造性风险；验证不支持时如何降低主张或放弃方向。优先给出少量有依据、能执行的方向，不凑固定数量。

如果经过适用范围的检索和材料核对仍没有可信方向，明确写出“当前未发现有依据的可推进方向”，并说明需要什么新技术事实、对照数据或方案变化才能重新判断。不得把“缩小权利要求”“补实验”本身包装成已经成立的创造性方案。

## 1. 先理解交底书

在检索前，先读取用户点名的交底书；需要确定保护对象、验证效果或复用已核结论时，再联读相关权要、实验、既有检索和技术文档。复用已有且未变化的事实记录。内部用条目记录，不要做成评述表格，实质分析至少包含：

- 技术对象：组合物、材料、装置、方法、产品、用途或其组合
- 技术目的：交底书声称要解决的问题，区分可核实事实和交底书表述
- 必要特征：组成、结构、步骤、顺序、参数和必要条件
- 特征关系：组分之间、结构之间或步骤之间的作用关系
- 可选特征：备选材料、范围、工艺条件和从属方案
- 主张效果：已有数据、定性观察或尚待验证的效果
- 证据状态：已知事实、合理推断或待证事项

不要把反应机理、投料目的或单一表征峰位直接当成已经形成的结构或化学键。

AnyDoc 转出 Markdown 不等于交底已读完。转换后先核空洞，再拆特征。有 Markdown 但出现任一情况，按下面补读，不要当全文：

- 正文有「如下式」「见图」「计算公式」等提示，后文没有对应式或图
- 章节只有标题、步骤跳号，或关键参数节为空
- 源文件明显大于抽出文本（Word 含图时常见）
- 旧版 `.doc`，或公式被贴成图

补读顺序：

1. 不整本 OCR，不把交底当扫描专利整份停住。
2. 从 Word/OOXML 抽对象：`word/media`、公式对象、OLE。能线性化的公式用文本；贴图只看缺的那些。用户已要求阅读该交底时，可在案件 `tmp` 把 `.doc` 另存为工作副本再抽，不改原件。覆盖原件或用 LibreOffice 整本转换，仍须先征得同意。
3. 抽出的公式图、谱图直接看图转写。图证与文字证据分开写。图与正文冲突时记下冲突，不以图覆盖正文，也不把未看的图补成事实。
4. 转写进入 `workbench/01_交底事实与术语.md` 并标明图证。`tmp` 可留抽取底稿，不另建案件正文「公式转写.md」。
5. 整页皆扫描、对象也拆不出：停，请用户提供可复制文本或指定看哪些页。仅对缺的那页或那图做识别时，标「待核」，不得当已校对事实写进评述或权要。不要安装 OCR 引擎处理整份文件。

对比文件专利的扫描件、图片型 PDF 仍按第 4 节处理。

## 2. 提取检索要素和检索式

从技术特征表中分别提取：

1. 技术对象和应用场景；
2. 核心组分、结构或材料名称；
3. 组分/结构之间的关系；
4. 工艺步骤、顺序和必要条件；
5. 性能目标及可测参数；
6. 中文、英文、缩写、上位概念和下位概念。

先用结构和核心组分构造窄检索式，再逐步删除一个限定组或改用上位概念扩大。机理词另设辅助检索式，不把机理作为唯一必要特征。记录实际使用的检索式、平台、日期和筛选范围。

需要专利检索时，先发现可调用的 HimmPat `product_patent_discovery` 业务工具，以本案第一条实际查询验证；成功即继续使用，不额外做无业务用途的探测。同一任务中已成功调用且连接未变化时，无须重复验证。`initialize` 和 `tools/list` 属于 MCP 客户端协议操作，仅在连接诊断时按实际环境处理；不要求模型取得未暴露的协议接口，也不以工具名暂未显示、通用 `resources/list` 或网页登录状态判断业务不可用。

只有业务工具经发现后仍不可用，或连接、业务调用、认证失败时，才按 Exa → 当前 agent 的上网/浏览能力 → 用户分组检索式的顺序降级，记录实际渠道和失败原因。HimmPat 网页会话与 API Bearer 密钥是两条路径。仅在需要页面查看或用户明确要求网页下载时，读取工作区 [归档网页操作流程](../../archive/已归档-HimmPat专利检索-Agent工作流.md)。Exa 也可用于论文等非专利资料发现；摘要、高亮和语义命中只用于初筛，正式判断仍须回到可核验全文。

如果明确执行 HimmPat 网页操作且页面提示“当前登录已过期”，暂停页面操作并请用户在 In-App Browser 中重新登录；不要读取账号、密码、cookies、localStorage 或令牌。页面登录失效不等于 API MCP 不可用；业务失败按本节规则降级，不得把其他来源标作 HimmPat 结果。

### 输出给用户自行检索的组合式

每轮检索前先把关键词整理成 2～8 个有意义的语义单位，并同时给出可复制的组合式。`/TAC` 仅在目标平台支持时使用；英文完整词组用双引号包住。不要把一整句长中文作为唯一检索词，也不要把单字或泛词硬凑在一起。

建议至少输出以下四类，按案件实际情况删减：

```text
窄检索：
(对象词1 OR 对象词2) AND (核心组分/结构词1 OR 核心组分/结构词2) AND (用途/场景词1 OR 用途/场景词2)

关系/工艺检索：
(核心组分/结构词) AND (关系词1 OR 关系词2) AND (工艺步骤/条件词1 OR 工艺步骤/条件词2)

效果检索：
(对象词 OR 上位对象词) AND (核心组分/结构词) AND (性能目标1 OR 性能目标2)

机理辅助检索：
(核心组分/结构词) AND (迁移/键合/交联等机理词) AND (用途/场景词)
```

先运行窄检索；结果不足时删除限定组或改用上位概念扩大，并在记录中标明“窄检索/扩大检索/机理辅助检索”。工具选择和降级遵循本节业务验证规则。

## 3. 候选文件和用户交接

候选文件至少记录：公开号、标题、申请人、申请日、公开日、同族关系、检索来源、命中特征、初步相关性和建议用途。

按以下类别归档：

- 直接相关：可能影响新颖性或作为最接近现有技术；
- 组合相关：可能用于创造性启示分析；
- 背景相关：用于说明通用技术或效果；
- 同族重复/语义误命中：记录原因后排除。

向用户交付“待下载清单”，说明哪些文件需要完整文本和优先级。清单来源可以是 HimmPat、Exa 或其他明确标注的渠道。用户将文件放入对应案件目录后，再继续深入分析。

检索与写入分开：检索阶段尽量充分，候选可以多；评述正文通常只写入 1 件最接近现有技术，另加 1～2 件真正能补区别或构成结合风险的辅助文件，合计约 3 件。其余直接相关、组合相关文件留在工作底稿，评述里最多一笔带过。不要因为检索到很多就全部写入，也不要为凑三件而把背景文件写成对比文件。区别数量与文件数量彼此独立，不要互相凑数。

### Exa 结果的对比文件交接

Exa 返回的资料可能包括专利、论文、学位论文、会议资料、预印本、技术报告和网页。对于明显有助于创造性分析的结果，即使页面无法直接打开、存在付费墙或只能看到摘要，也要单独列为“Exa 候选待取得全文”，并向用户提供：

- 标题、作者/申请人、公开编号或 DOI、年份和原始 URL；
- Exa 结果中可核验的技术对象、核心手段、应用场景和命中特征；
- 为什么值得作为文件1、组合启示文件或背景文件；
- 哪些内容尚未核实，用户需要下载或提供什么全文材料。

不得把 Exa 摘要或高亮直接当作完整公开内容，也不得把付费墙后的推测写成文件事实。用户取得 PDF、公开专利文本或其他可读全文后，按同一“文件核验”流程处理。

## 4. 文件核验

不得仅凭标题、搜索摘要或语义命中下最终结论。读取用户下载的全文并记录：

- 每个特征的具体出处（权利要求、说明书段落、附图或实施例）；
- 是明确公开、可由明确组合得到，还是仅为可选列表中的可能选择；
- 文件的公开日、申请日、优先权和同族关系；
- 文件实际解决的问题、采用的手段和证明的效果；
- 与本案相同、相近或相反的内容。

在案件尚未提交时，文献先称为“检索到的公开文献/现有技术候选”。确定申请日或最早优先权日后，再判断其法律时间属性。

### 文档读取降级

先区分文件种类。交底书的嵌图、公式贴图按第 1 节补读，不要按扫描件整份停。本节管对比文件全文。

含可提取文本的 DOCX、PPTX、XLSX 和案件对比文件 PDF 优先使用 AnyDoc 转 Markdown；AnyDoc 不可用或格式不支持时，对 DOCX 改用 Python/OOXML 等直接读取，并注明实际方法。《专利审查指南》按 `examination-guidelines.md` 用 `pypdf` 抽对应章，不要整本 AnyDoc。扫描件或图片型 PDF 不安装 OCR：停下来，请用户从 HimmPat、CNIPA 等复制权利要求、说明书及著录项，或提供可提取文本的同族文件，并注明文本来源。未经用户明确要求，不要逐页截图，也不要用 HimmPat 读专利细节来绕过。用户已提供文字后，若关键事实仍只在图中且用户要求核对，再按页看图并记录页码。不得把未查看的图像或机器摘要当作全文事实，也不得用识别结果代替官方权要文本。

## 5. 按独立权利要求选择最接近现有技术

组合物、制备方法、涂层、产品和用途可能分别有不同的最接近文件。对每项独立权利要求分别比较候选文件：

1. 技术领域是否相同或相近；
2. 技术目的或应用场景是否最接近；
3. 公开的必要技术特征数量和组合关系是否最多；
4. 是否适合作为后续区别和技术问题分析的起点。

选择结论必须说明理由，不能只因为某文件命中特征最多就机械指定。

## 6. 文件1与本案的逐项比对

对每项独立权利要求用条目核对：该特征在对比文件1中的出处、公开强度（明确 / 组合可得 / 未公开），以及是否保留为区别。不要把这张对照表写入评述正文。

随后列出拟保护独权相对该文件的实际区别。编号按独立技术含义和特征间关系组织，不为匹配辅助文件拆分。判断区别时核对：

1. 对比文件1未公开；
2. 拟作为该项独立权利要求的必要特征；
3. 属于有依据的技术限定；结构、组成、工艺、参数或用途按其实际限定作用判断，未证实机理或未测性能不得作为确定事实；
4. 效果及证据状态单列评价，不因缺少独立对照就抹去客观存在的技术差异。

有几项写几项。一项就写一项；够了可以写多项。不要为了配辅助文件而把一项拆成三项。

用途、黏度、工艺窗口和基材等是否构成区别，先看拟保护独权的实际限定及文件公开内容，不按词类一概排除；是否单独编号取决于技术含义和关系，是否支持创造性则取决于效果依据和结合启示。工艺步骤若只影响制备过程，放入方法权利要求评述。未写入拟保护独权的内容不混入该项区别。

如果“分别加入”“未预先复合”等是制备过程特征，要判断它是否应当放入方法权利要求；产品权利要求只有在最终结构、组成状态或可测性能形成区别时才将其作为产品区别。

## 7. 区别效果和实际技术问题

每个区别特征都要对应技术效果，并标记证据等级：

- 已由相同条件下的对照实验支持；
- 有实施例或表征，但缺少关键对照；
- 基于技术常识的合理推断；
- 仅为交底书中的假设或机理设想。

只有已证明或至少有可靠直接依据的效果，才能用于构造创造性论证。尚缺独立效果依据的区别保留其公开内容比对，但不得据此倒推性能提高；相互作用的特征可评价共同效果。根据有依据的效果确定客观技术问题，技术问题不得直接写入本案的技术方案、具体组分或未证实机理。证据不足时说明可支持的较保守问题或保留待决事项。本节对应 Ⅱ.Ⅳ-3.2.1.1 的「实际解决的技术问题」，不是说明书 2.2.4 的撰写问题；两类问题的区分见 `examination-guidelines.md`。

## 8. 其他文件的启示分析

先按实际公开内容写该辅助文件公开了什么、要解决什么问题、证明了什么效果，再写它实际碰到了哪些编号区别、没碰到哪些。一件文件可以评多项区别，一项区别也可以没有任何辅助文件覆盖。禁止预先指定「对比文件2对区别1、对比文件3对区别2」。某项区别现有辅助文件都未覆盖时，直接写明，这有利于创造性，不要再找一篇文件来配对。

辅助文件通常 1～2 件即可。选择标准是：能补对比文件1未公开的结构或工艺，或构成针对本案技术问题的结合风险。应用场景相近但问题、填料都不同的文件，可以保留一件挡住「场景常规、工艺可迁移」；不要因为它碰巧像某一项弱区别就硬配上去。

每件辅助文件回答：

1. 是否属于相同或相近技术领域；
2. 是否解决相同或相近的技术问题；
3. 技术手段能否直接替换或迁移；
4. 是否存在明确结合启示，而不只是“理论上可以”；
5. 结合后是否有合理成功预期；
6. 是否存在相反教导、技术偏见、参数不兼容或需要多重选择。

辅助文件不能拼接用于否定新颖性。若组合需要同时改变材料、结构、工艺和参数，应记录这些额外改动以及是否属于事后拼接。

## 9. 创造性结论

按独立权利要求分别给出：

- 单件文件是否完整公开全部必要特征；
- 评述中实际写入的文件各自覆盖哪些特征，不要把未写入评述的检索结果拼进来下结论；
- 创造性风险等级及其具体理由；
- 结论依赖的已证效果；
- 目前缺失的全文证据或实验；
- 可保留的核心特征和可下沉的从属特征。

“未找到完全相同文件”只能说明尚未作出单件新颖性缺失结论，不能自动推出创造性成立。

## 10. 反馈给申请文本

创造性检索分析完成后，单独列出申请文本接口：

- 建议进入独立权利要求的必要技术特征；
- 建议作为从属权利要求的材料、关系、顺序或参数限定；
- 可以写入说明书的技术问题和效果；
- 只能作为待验证假设的机理；
- 需要补充的实施例、对照例和测试条件，交给实验设计节点，不要在评述里展开配方表；
- 因现有技术风险不宜维持的宽泛表述。

如果下一步起草权利要求，读取 `references/claim-drafting-workflow.md` 和 `references/claim-drafting-template.md`。如果下一步排实验，读取 `references/experimental-design-workflow.md`。检索分析只提供当前方案的风险、区别和证据接口；独立权利要求的宽度、从属层级和具体文字应按权利要求模块重新组织，不能把本评述中的文件组合论证直接复制进去。

检索分析中的文件组合、审查员攻击路径和法律判断用于内部决策；申请文件应将其转换为中性的背景技术、明确的技术方案和有证据支持的效果表述。
