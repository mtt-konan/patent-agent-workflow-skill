# 权利要求撰写工作流

## 目标和边界

本工作流用于申请前从技术交底书和创造性检索结果起草权利要求书。目标是在有支持基础的范围内保留合理的保护空间，并通过多档从属权利要求保留具体退让路径。

本文件只固化权利要求模块，不代替说明书、具体实施例、实验设计或审查意见答复规则。权利要求中的每个技术限定都应能回到交底事实、已核对的技术资料或后续明确的说明书支撑计划；不能为了做宽而补造技术内容。

## 输入和前提

起草前应确认：

- 当前技术方案版本，例如 `V1` 或 `V2`；方案实质变化后不得混用旧版本特征；
- 交底书中明确记载的技术对象、必要特征、可选特征、特征关系和已有效果；
- 创造性检索分析中的最接近现有技术、区别特征、证据状态、风险特征和可下沉特征；评述第三节和第二节将进入说明书，权要不要另写一套技术问题或效果；
- 工作底稿中的特征—文件—效果—证据关系，以及尚待确认或补实验的事项；
- 是否存在多个具有独立保护价值的对象，如组合物/材料、产品、制备方法或用途。

如果当前方案的创造性结论尚未稳定，先在工作底稿中记录待决问题；不要用猜测性的窄限定代替方案判断。

由 `SKILL.md` 进入权要节点后再读本文件。不要因为打开本文件就重跑检索或代写说明书。用户只要讨论架构、宽度或独权对象时先讨论，不要急于改权利要求文件；要求改已有权要时只改权要相关部分，除非同时要求改说明书。

## 1. 确定权利要求架构

先按技术对象分组，再决定是否需要分别设置独立权利要求：

1. 组合物、材料或装置本身；
2. 由该方案得到的最终产品或应用对象；
3. 制备、组装或使用方法；
4. 用途或处理方法。

不是每个类别都必须起草。只有该类别有独立的技术贡献、保护价值和交底支持时才设置独立权利要求。不同类别之间不能因为共用几个组分就机械重复。

每个独立权利要求先写一个内部特征清单，分为：

- 必要特征：缺少后无法界定本案要保护的技术方案，或无法实现要主张的技术效果；
- 可选特征：适合作为从属限定或具体实施方式；
- 待证特征：机理、结构状态、性能或参数尚无足够证据，不得直接作为确定的核心限定。

## 2. 起草独立权利要求

### 2.1 合理做宽

给甲方看的中间稿（含尚未提交的 V1）独立权利要求以合理做宽为目标。检索用来划新颖性边界、把对着最接近文件的退路写入从属或方法独权、并设计对照实验；不是找到最接近文件就把独权改写成规避方案，也不是按预判的一通写成实施例的最窄形式。实验方法、方案和结果出来后，再决定维持该宽度或从已经写好的从属里收窄。提交前可以收；中间稿默认先宽。一通、二通只能在原申请记载范围内改窄，申请日独权是保护面的上限。

宽度应同时受以下边界约束：

1. 交底书确实公开或能够明确概括该上位范围；
2. 说明书后续能够对术语、组成、结构关系、替代方案和实施方式提供充分支撑；
3. 独立权利要求仍然由具有技术意义的结构、组成、步骤或关系限定，而不是只写目标、效果或愿望；
4. 单篇对比文件已经无歧义公开的组合，独权不能再那样写；其余风险高的限定放入从属或方法独权作为退路，而不是提前塞进产品独权；
5. 不能把尚未验证的机理、协同作用、化学键、网络结构或性能提升写成确定限定。

“做宽”通常意味着只保留必要的核心组合，暂不把所有优选材料、具体比例、窄参数、加料顺序和单个实施例条件写入独立权利要求，而不是使用没有边界的“任意”“等”或泛化到交底书无法支持的上位概念。

### 2.2 技术限定的组织

独立权利要求应围绕一个明确的保护对象组织：

- 产品、组合物或装置权利要求重点写组成、结构及其必要关系；
- 方法权利要求重点写必要步骤、步骤关系、顺序和关键条件；
- 用途权利要求重点写明确的使用对象、用途关系和必要操作；
- 仅影响制备过程的特征原则上放入方法权利要求；只有在最终产品形成可识别的组成、结构或状态区别时，才作为产品权利要求的限定。

功能或结果限定只有在能够清楚界定技术边界、且有说明书和技术依据时才使用。不能用“提高性能”“改善稳定性”等结果句替代实现该结果的技术特征。

避免使用没有明确边界的“适当”“较高”“优选”“等”以及无法判断范围的纯效果表述。化学名称、材料名称、参数单位和缩写必须与交底书和说明书保持一致。

## 3. 设置从属权利要求的后备层级

从属权利要求必须包含父项的全部限定，并增加至少一个有技术意义的具体限定。后备方案按案件实际情况逐级设置，不要求固定数量，但应形成从宽到窄的保护梯度：

1. 结构或组分关系层：进一步限定连接、分布、相态、位置、比例关系或步骤顺序；
2. 材料和组成层：限定优选材料、材料类别、取代范围或组合方式；
3. 参数和工艺层：限定粒径、浓度、质量比、温度、时间、pH、压力或其他有依据的条件；
4. 实施例组合层：收纳交底书中已经实施或明确计划实施的具体组合；
5. 性能层：只有在测试方法、对照条件和结果已有可靠依据时，才加入性能阈值或效果限定。

设置从属权利要求时：

- 每一项都要能在说明书中找到依据，并说明它为何是有意义的后备路径；
- 优先保留能与最接近现有技术拉开距离的结构、组成或工艺关系；
- 不要把所有材料、数值区间和可能用途机械并列，避免产生大量重复或互相矛盾的权利要求；
- 从属项之间可以并列，也可以形成递进依附，但依附关系必须清楚，不能因多重引用造成范围不明；
- 尚无证据的特征可列入待补清单，不得为了填满后备层级而写入确定权利要求。

## 4. 使用检索结果调整保护范围

检索结果进入权利要求时按以下链条处理：

```text
文件公开了什么
→ 对应本案哪些特征
→ 哪些特征仍能作为当前版本的必要区别
→ 哪些特征适合下沉为从属限定
→ 哪些特征需要说明书或实验补足
```

对比文件不是权利要求的来源，也不是权利要求正文的写作对象。不得把“对比文件1未公开”“对比文件2没有结合启示”等审查员式判断写进权利要求。

如果检索发现独立权利要求的核心组合风险较高，应依次考虑：

1. 是否只是检索不充分，需要补充检索；
2. 是否只是效果证据不足，需要补实验或降低效果表述；
3. 是否应把某一非必要限定下沉为从属权利要求；
4. 是否核心技术方案已经与现有技术重合，需要形成新的方案版本并重新检索。

不能为了规避单篇文件而任意拼接多个没有技术关系的限定。新增限定必须属于当前方案并有技术意义。已经确定最接近文件后，不要立刻把产品独权写成对该文件的规避文本；把能拉开距离的结构、组成或工艺关系写入从属或方法独权即可。

## 5. 建立权利要求—说明书支撑接口

权利要求草案完成后，对每一项权利要求至少记录：

- 技术对象和保护层级；
- 每个限定的交底依据或现有材料出处；
- 需要在说明书中定义的术语和范围；
- 需要列出的替代材料、结构、步骤或参数；
- 能够覆盖该限定的实施方式或实施例；
- 需要补充的对照实验、测试方法和数据；
- 当前是已知事实、合理推断还是待证事项。

独立权利要求越宽，说明书需要铺设的替代方案和实施支持越充分。没有支撑的宽泛表述应当标记为“待补支持”或收窄，而不是默认为可以写入。

## 6. 权利要求审计

交付前至少检查：

1. 版本：所有权利要求是否只对应当前技术方案版本；
2. 对象：每项独立权利要求是否围绕一个明确对象，类别是否写对；
3. 必要性：独立权利要求是否只保留必要且有技术意义的限定；
4. 宽度：上位概念是否有交底事实和说明书支撑；给甲方的中间稿是否把加料顺序、功能限定或窄参数不必要地写进产品独权；
5. 依附：从属权利要求是否包含父项全部限定，新增限定是否明确；
6. 梯度：从属权利要求是否形成至少两档有意义的具体后备路径，是否存在重复或断档；
7. 检索：独权相对单篇对比文件是否具备新颖性；对着最接近文件的退路是否已写入从属或方法独权；区别特征是否来自当前方案；
8. 证据：机理、效果、参数和性能是否与证据状态一致；
9. 一致性：名称、术语、缩写、数字、单位和技术关系是否前后一致；
10. 接口：说明书需要补充的支撑和实验事项是否已列出。

审计发现问题时，先修改权利要求结构或标记待补事项，不要用未经证实的机理和效果填补逻辑缺口。

## 7. 输出

使用 `references/claim-drafting-template.md` 形成案件目录中的权利要求书 Markdown。模板中的内部特征映射和支撑清单用于工作连续性；交付给甲方或整理为正式申请文件前，应删除不属于权利要求正文的内部备注。

说明书按 `references/specification-drafting-workflow.md` 起草。需要补充的对照实验按 `references/experimental-design-workflow.md` 排表。权利要求阶段仍输出支撑接口；不要虚构实验结果。
